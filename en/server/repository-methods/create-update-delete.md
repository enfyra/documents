# Create, Update, and Delete Records

## Create

Create a new record in the table. Automatically returns the full created record including ID and timestamps.

### Basic Usage

```javascript
const result = await $ctx.$repos.products.create({
  data: {
    name: 'New Product',
    price: 99.99,
    category: 'electronics'
  }
});

const newProduct = result.data[0];  // Full product record with ID, timestamps, etc.
```

### Parameters

```javascript
await $ctx.$repos.tableName.create({
  data: { ... },       // Data to insert (required)
  fields: '...'        // Fields to return (optional)
})
```

### Creating Records

#### Simple create
```javascript
const result = await $ctx.$repos.products.create({
  data: {
    name: 'iPhone 15',
    price: 999,
    category: 'electronics'
  }
});
```

#### Create with all fields
```javascript
const result = await $ctx.$repos.products.create({
  data: {
    name: 'iPhone 15',
    price: 999,
    category: 'electronics',
    description: 'Latest iPhone model',
    isActive: true,
    stock: 50
  }
});
```

#### Return specific fields after create
```javascript
const result = await $ctx.$repos.products.create({
  data: {
    name: 'iPhone 15',
    price: 999
  },
  fields: 'id,name,price'  // Only return these fields
});
```

### Important Notes

1. **ID is auto-generated**: Never include `id` in the data object - it will be automatically generated by the database
2. **Timestamps are auto-generated**: `createdAt` and `updatedAt` are automatically added by the system
3. **Full record is returned**: The method automatically calls `find()` after insertion to return the complete record
4. **Validation happens automatically**: System validates table schema and system protection rules

### Create with Relations

```javascript
// Create order with related items
const orderResult = await $ctx.$repos.orders.create({
  data: {
    customerId: 123,
    total: 299.99,
    status: 'pending'
  }
});

const order = orderResult.data[0];

// Create order items
const itemResult = await $ctx.$repos.order_items.create({
  data: {
    orderId: order.id,
    productId: 456,
    quantity: 2,
    price: 149.99
  }
});
```

### Error Handling

```javascript
try {
  const result = await $ctx.$repos.products.create({
    data: {
      name: 'Product Name',
      price: 99.99
    }
  });
} catch (error) {
  // Handle validation errors, constraint violations, etc.
  $ctx.$logs(`Failed to create product: ${error.message}`);
}
```

## Update

Update an existing record by ID. Automatically returns the full updated record.

### Basic Usage

```javascript
const result = await $ctx.$repos.products.update({
  id: 123,
  data: {
    price: 89.99,
    isOnSale: true
  }
});

const updatedProduct = result.data[0];  // Full updated product record
```

### Parameters

```javascript
await $ctx.$repos.tableName.update({
  id: 123,              // Record ID to update (required)
  data: { ... },        // Fields to update (required)
  fields: '...'         // Fields to return (optional)
})
```

### Updating Records

#### Update single field
```javascript
const result = await $ctx.$repos.products.update({
  id: 123,
  data: {
    price: 89.99
  }
});
```

#### Update multiple fields
```javascript
const result = await $ctx.$repos.products.update({
  id: 123,
  data: {
    price: 89.99,
    isOnSale: true,
    description: 'Updated description'
  }
});
```

#### Return specific fields after update
```javascript
const result = await $ctx.$repos.products.update({
  id: 123,
  data: {
    price: 89.99
  },
  fields: 'id,name,price'  // Only return these fields
});
```

### Important Notes

1. **ID must exist**: The record with the given ID must exist, otherwise an error is thrown
2. **Partial updates**: You only need to include fields you want to update
3. **Full record is returned**: The method automatically calls `find()` after update to return the complete record
4. **Timestamps are auto-updated**: `updatedAt` is automatically updated by the system
5. **Validation happens automatically**: System validates table schema and system protection rules

### Check if Record Exists First

```javascript
// Find the record first
const findResult = await $ctx.$repos.products.find({
  filter: { id: { _eq: 123 } }
});

if (findResult.data.length === 0) {
  @THROW404('Product not found');
  return;
}

// Update the record
const result = await $ctx.$repos.products.update({
  id: 123,
  data: {
    price: 89.99
  }
});
```

### Error Handling

```javascript
try {
  const result = await $ctx.$repos.products.update({
    id: 123,
    data: {
      price: 89.99
    }
  });
} catch (error) {
  // Handle errors: record not found, validation errors, etc.
  $ctx.$logs(`Failed to update product: ${error.message}`);
}
```

## Protected Read-Modify-Write with `updateLocked`

Use `updateLocked` when a new value depends on the persisted record, such as deducting credit or changing a state after checking its current value. Pass one options object with the same keys as `update`: `id`, optional `fields`, and `data`. Here, `data` is a callback that receives the record inside the protected database scope and returns a partial record to persist.

```javascript
const amount = Number(@BODY.amount);
if (!Number.isFinite(amount) || amount <= 0) @THROW400("amount must be positive");

const result = await #secure.accounts.updateLocked({
  id: @PARAMS.id,
  fields: ['credit', 'status'],
  data: (current) => {
    if (current.credit < amount) @THROW400("Insufficient credit");
    return {
      credit: current.credit - amount,
      status: 'active'
    };
  }
});

return result.data[0];
```

The computed `credit` and literal `status` returned by `data` are persisted together. The optional top-level `fields` only selects the response, exactly as in `update`; it does not select what is locked or written. Omit it to use the normal mutation response projection. Callback state is loaded independently of request pagination, field projection, and deep query options.

| Backend | Protection |
|---|---|
| PostgreSQL and MySQL/InnoDB | A primary transaction locks the root record with `SELECT ... FOR UPDATE` before invoking the callback. |
| MongoDB with native transactions | The read, callback, and write share a native transaction. A retryable write conflict reruns the transaction, reads the record again, and recomputes the patch. |
| MongoDB standalone or an application saga scope | Unsupported; the method fails without invoking the callback. |

Keep the `data` callback limited to computation, business validation, and returning the partial record. It can run more than once on MongoDB, so do not send HTTP requests, change cache/storage, emit socket events, trigger flows, or call other repositories inside it. Every retry must compute from its supplied `current`; do not calculate the replacement value from an earlier read. Apply owner/tenant checks that depend on current state inside the callback.

`updateLocked` supports plain generic tables. Schema/metadata routes and tables with custom update normalization or lifecycle handlers are rejected. The normal mutation policy, field permissions, updatable-field rules, and cascade processing still apply. A secure repository exposes only readable fields to the callback; `#accounts` remains intentional trusted access.

The method starts a transaction or joins the active one. When it joins an outer transaction, the outer scope owns commit, rollback, and MongoDB retry. Repository cache invalidations and mutation events are emitted after commit; rolled-back and retried attempts do not emit their effects. Automatic SQL lock waiting and a newly started MongoDB transaction are bounded to 30 seconds, and script cancellation remains in effect.

On PostgreSQL/MySQL, the row lock is retained until the outer transaction commits or rolls back; completion of the `data` callback does not release it. Callback state and update-policy checks use locking reads, so an earlier MySQL repeatable-read snapshot cannot supply an old root value. Keep other repository operations in the outer transaction, outside the pure `data` callback. Use [`findLocked`](./find.md#findlocked) when the common owner must be locked before those dependent reads; verify the deployed runtime supports it.

Root-record protection does not make unrelated records or external systems part of the same invariant. A client submitting an old absolute value still needs a separate state/revision precondition. Missing records, invalid callback results, and exhausted transaction retries are reported as errors rather than successful updates.

## Delete

Delete a record by ID. Returns a success message.

### Basic Usage

```javascript
const result = await $ctx.$repos.products.delete({
  id: 123
});

// result: { message: 'Delete successfully!', statusCode: 200 }
```

### Parameters

```javascript
await $ctx.$repos.tableName.delete({
  id: 123  // Record ID to delete (required)
})
```

### Deleting Records

#### Simple delete
```javascript
const result = await $ctx.$repos.products.delete({
  id: 123
});
```

#### Check if record exists before deleting
```javascript
// Find the record first
const findResult = await $ctx.$repos.products.find({
  filter: { id: { _eq: 123 } }
});

if (findResult.data.length === 0) {
  @THROW404('Product not found');
  return;
}

// Delete the record
const result = await $ctx.$repos.products.delete({
  id: 123
});
```

### Important Notes

1. **ID must exist**: The record with the given ID must exist, otherwise an error is thrown
2. **Cascade behavior**: If the table has relations with `onDelete: 'cascade'`, related records will be deleted automatically
3. **Returns success message**: The method returns `{ message: 'Delete successfully!', statusCode: 200 }`
4. **Cannot be undone**: Deletion is permanent - make sure to validate before deleting

### Error Handling

```javascript
try {
  const result = await $ctx.$repos.products.delete({
    id: 123
  });
} catch (error) {
  // Handle errors: record not found, constraint violations, etc.
  $ctx.$logs(`Failed to delete product: ${error.message}`);
}
```

## Batch create, update, and delete

Use batch repository methods only in dynamic handlers, hooks, and flows. Generated REST CRUD endpoints remain single-record endpoints.

Batch methods are deliberately limited to plain generic tables. Enfyra rejects schema/metadata tables and tables with custom normalization or lifecycle behavior. It validates and authorizes every supplied target before one bulk write, then runs one runtime reload and emits one mutation event. Use a secure repository for user-facing code and still enforce owner, tenant, and membership rules in the handler.

### Create many

```javascript
const result = await $ctx.$repos.secure.products.createMany({
  data: [
    { name: 'Keyboard', price: 99.99 },
    { name: 'Mouse', price: 49.99 }
  ],
  fields: ['id', 'name', 'price']
});

// result.data contains created records; result.count is 2
```

### Update many

`updateMany` applies the same data object to every ID. It does not accept relation payloads; update one record at a time when relation changes are required.

```javascript
const result = await $ctx.$repos.secure.products.updateMany({
  ids: [101, 102, 103],
  data: { isActive: false },
  fields: ['id', 'isActive']
});

// result.data contains updated records; result.count is 3
```

### Delete many

```javascript
const result = await $ctx.$repos.secure.products.deleteMany({
  ids: [101, 102, 103]
});

// result: { message: 'Delete successfully!', statusCode: 200, count: 3 }
```
